# Todo Python — Docker & Kubernetes Lab

A beginner-friendly Todo application with a Python/Flask REST backend and a Python/Flask server-rendered frontend.

```
Todo-python/
├── backend/
│   ├── app.py            # REST API (Flask)
│   ├── requirements.txt
│   ├── .dockerignore     # files Docker must not copy into the image
│   └── .gitignore        # files Git must not track
├── frontend/
│   ├── app.py            # Web UI (Flask + Jinja2)
│   ├── requirements.txt
│   ├── .dockerignore
│   ├── .gitignore
│   └── templates/
│       └── index.html
└── README.md             ← you are here
```

> **Environments used in this lab**
> - Docker sections → **GitHub Codespaces** (ports are auto-forwarded to your browser)
> - Kubernetes sections → **KillerKoda** free playground (NodePort is accessible via the built-in traffic button)

## 2 — .gitignore and .dockerignore

Both files live in `backend/` and `frontend/`. They contain the same entries because the files you
want to keep out of Git are also the files you want to keep out of Docker images.

```
__pycache__/   ← compiled Python bytecode — regenerated automatically, never commit or copy
*.pyc          ← individual compiled files
*.pyo          ← optimised compiled files
.env           ← local secrets (API keys, passwords) — must never leave your machine
.venv/ venv/   ← virtual environment folder — large and machine-specific
*.egg-info/    ← package metadata generated by setuptools
.pytest_cache/ ← test runner cache
```

### .gitignore

Tells Git which files to leave untracked. Without it you would accidentally commit `__pycache__`
folders, your local `.env` file with secrets, or a 200 MB `venv/` directory.

```bash
# verify what Git will ignore before committing
git status
git check-ignore -v __pycache__   # prints the rule that matched
```

### .dockerignore

Tells the Docker build daemon which files to exclude from the **build context** — the set of
files sent to Docker before it runs your Dockerfile.

Without it, `COPY . .` copies everything including `__pycache__`, `.env`, and `venv/`.
That bloats the image and risks leaking secrets.

```bash
# check what your image actually contains after the build
docker run --rm todo-backend ls -la /app
```

The two files are separate because Git and Docker are separate tools, but keeping them in sync
with the same entries is the simplest approach for a project like this.

## 3 — Simple Dockerfiles

### What is a Dockerfile?

A Dockerfile is a plain-text recipe that tells Docker how to build an image for your app.
Each line is an instruction. Docker reads them top-to-bottom and layers the result.

### backend/Dockerfile

```dockerfile
# 1. Start from an official Python image
FROM python:3.12-slim

# 2. Set the working directory inside the container
WORKDIR /app

# 3. Copy dependency list first (improves layer caching)
COPY requirements.txt .

# 4. Install dependencies
RUN pip install --no-cache-dir -r requirements.txt

# 5. Copy the rest of the source code
COPY . .

# 6. Tell Docker which port the app uses (documentation only)
EXPOSE 5000

# 7. Command to start the app
CMD ["python", "app.py"]
```

### frontend/Dockerfile

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8080

CMD ["python", "app.py"]
```

### Build and run manually

```bash
# Build images
docker build -t todo-backend  ./backend
docker build -t todo-frontend ./frontend

# Create a shared network so containers can reach each other by name
docker network create todo-net

# Run backend
docker run -d --name backend --network todo-net -p 5000:5000 todo-backend

# Run frontend — pass the backend's container name as the URL
docker run -d --name frontend --network todo-net -p 8080:8080 \
  -e BACKEND_URL=http://backend:5000 \
  todo-frontend
```

**GitHub Codespaces:** the Ports panel auto-detects 8080 and gives you a public URL to click.
You do not need to do anything extra.

## 4 — Multi-stage Dockerfiles

### Why multi-stage?

A normal Dockerfile keeps every tool used during the build (compilers, pip cache) in the final
image, making it larger than necessary.
Multi-stage builds use one stage to install dependencies, then copy only what is needed into a
clean final image.

For Python the size reduction is modest, but the pattern is essential for compiled languages
(Go, Java, C++) so it is worth learning here.

### backend/Dockerfile (multi-stage)

```dockerfile
# ── Stage 1: builder ─────────────────────────────────────────────
FROM python:3.12-slim AS builder

WORKDIR /install

COPY requirements.txt .

# Install packages into a local prefix, not the system Python
RUN pip install --no-cache-dir --prefix=/install/packages -r requirements.txt

# ── Stage 2: runtime ─────────────────────────────────────────────
FROM python:3.12-slim

WORKDIR /app

# Copy only the installed packages from the builder stage
COPY --from=builder /install/packages /usr/local

# Copy application source
COPY . .

EXPOSE 5000

CMD ["python", "app.py"]
```

### frontend/Dockerfile (multi-stage)

```dockerfile
# ── Stage 1: builder ─────────────────────────────────────────────
FROM python:3.12-slim AS builder

WORKDIR /install

COPY requirements.txt .

RUN pip install --no-cache-dir --prefix=/install/packages -r requirements.txt

# ── Stage 2: runtime ─────────────────────────────────────────────
FROM python:3.12-slim

WORKDIR /app

COPY --from=builder /install/packages /usr/local

COPY . .

EXPOSE 8080

CMD ["python", "app.py"]
```

### Key terms

| Term | Meaning |
|------|---------|
| `AS builder` | Names a stage so later stages can reference it |
| `COPY --from=builder` | Copies files from a previous stage instead of from the host |
| Final image | Only the last stage ends up in the image — builder layers are thrown away |

## 5 — Docker Compose

### What is Docker Compose?

Docker Compose lets you start multiple containers with a single command using one
`docker-compose.yml` file. No long `docker run` commands, no manual network creation.

### docker-compose.yml (place at Todo-python/)

```yaml
version: "3.9"

services:

  backend:
    build: ./backend          # builds from ./backend/Dockerfile
    container_name: backend
    ports:
      - "5000:5000"           # useful for direct API testing
    networks:
      - todo-net

  frontend:
    build: ./frontend         # builds from ./frontend/Dockerfile
    container_name: frontend
    ports:
      - "8080:8080"           # browser connects here
    environment:
      - BACKEND_URL=http://backend:5000   # service name "backend" acts as hostname
    depends_on:
      - backend               # Compose starts backend before frontend
    networks:
      - todo-net

networks:
  todo-net:
    driver: bridge            # both containers share this network and can find each other by name
```

### How the two services talk to each other

Docker Compose creates automatic DNS on the shared network.
The service name (`backend`) becomes the hostname inside every other container on that network.
So `http://backend:5000` in the frontend code resolves to the backend container — no IPs needed.

### Useful Compose commands

```bash
# Start everything (builds images on first run)
docker compose up

# Start in the background
docker compose up -d

# Stream logs from all services
docker compose logs -f

# Stream logs from one service only
docker compose logs -f backend

# Stop and remove containers (images are kept)
docker compose down

# Stop, remove containers AND delete images
docker compose down --rmi all

# Rebuild images after a code change and restart
docker compose up --build
```

**GitHub Codespaces:** after `docker compose up`, both port 5000 and 8080 appear in the Ports
panel. Click the link for 8080 to open the app.

## 6 — Kubernetes Deployment

### Key concepts (quick reference)

| Object | Purpose |
|--------|---------|
| **Deployment** | Keeps a set of identical Pods (containers) running |
| **Service** | Gives a stable name and address to a group of Pods |
| **ClusterIP** | Service type — reachable only inside the cluster. Used for the backend. |
| **NodePort** | Service type — opens a fixed port on every cluster node so external traffic can reach the Pod. Used for the frontend. |
| **ConfigMap** | Key-value store for configuration. Injected as environment variables — no config baked into the image. |

---

### How frontend and backend talk inside Kubernetes

Kubernetes automatically creates DNS entries for every Service.
If a Service is named `backend`, any Pod in the same namespace can reach it at `http://backend:5000`.
No IP addresses, no host entries required.

We put that URL in a ConfigMap and inject it as the `BACKEND_URL` environment variable.
The frontend code reads `BACKEND_URL` from the environment — the same code works everywhere.

```
Browser (NodePort 30080)
        │
        ▼
  frontend Pod  ──── http://backend:5000 (ClusterIP DNS) ────▶  backend Pod
```

### File layout for manifests

```
k8s/
├── configmap.yaml
├── backend-deployment.yaml
├── backend-service.yaml
├── frontend-deployment.yaml
└── frontend-service.yaml
```

---

### ConfigMap

```yaml
# k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: todo-config
data:
  BACKEND_URL: "http://backend:5000"
  # "backend" is the name of the backend Service.
  # Kubernetes DNS resolves it automatically inside the cluster.
```

---

### Backend — Deployment & Service

```yaml
# k8s/backend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: backend
          image: todo-backend:latest
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 5000
```

```yaml
# k8s/backend-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: backend             # this name is the DNS hostname used by the frontend
spec:
  type: ClusterIP           # private — only reachable from inside the cluster
  selector:
    app: backend
  ports:
    - port: 5000
      targetPort: 5000
```

---

### Frontend — Deployment & Service

```yaml
# k8s/frontend-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
spec:
  replicas: 1
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
        - name: frontend
          image: todo-frontend:latest
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          env:
            - name: BACKEND_URL
              valueFrom:
                configMapKeyRef:
                  name: todo-config   # the ConfigMap defined above
                  key: BACKEND_URL
```

```yaml
# k8s/frontend-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: frontend
spec:
  type: NodePort            # opens a port on the node so the browser can reach it
  selector:
    app: frontend
  ports:
    - port: 8080            # cluster-internal port
      targetPort: 8080      # port the container listens on
      nodePort: 30080       # port exposed on the node (browser uses this)
```

### Apply everything

```bash
# 1. Build and push images, or for KillerKoda pull from Docker Hub:
#    docker build -t <your-dockerhub-username>/todo-backend:latest ./backend
#    docker push <your-dockerhub-username>/todo-backend:latest
#    (then update image: in the Deployment YAML to match)

# 2. Apply all manifests
kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/backend-deployment.yaml
kubectl apply -f k8s/backend-service.yaml
kubectl apply -f k8s/frontend-deployment.yaml
kubectl apply -f k8s/frontend-service.yaml

# 3. Verify everything is up
kubectl get pods
kubectl get services
```

### Open in browser — KillerKoda

KillerKoda provides a **Traffic / Port** button in its UI.

1. Click the traffic button (or the port icon) in the KillerKoda toolbar.
2. Enter port **30080**.
3. KillerKoda opens a proxied URL directly to the frontend — no port-forward needed.

If you cannot find the button, you can also run:

```bash
curl http://localhost:30080
```

from the KillerKoda terminal to confirm the app is responding.

---

### Why this design?

| Decision | Reason |
|----------|--------|
| Backend = ClusterIP | The backend API is private. Only the frontend needs it. No reason to expose it outside the cluster. |
| Frontend = NodePort | You need browser access. NodePort exposes a port on the node directly — works out of the box on KillerKoda. |
| ConfigMap for BACKEND_URL | Config lives outside the image. Change the Service name or port → update the ConfigMap only, no rebuild. |
| DNS via Service name | Kubernetes resolves `backend` to the correct Pod IP automatically. You never hard-code addresses. |
